# T3-owned orchestration

T3 owns delegated-task lifecycle; its selected provider runs the model. Implement the generic
[harness contract](../harness.md) and [orchestration](../orchestration.md), not provider/plugin assumptions.

## Dispatch and ownership

- Discover live provider/model IDs and options with `orchestrator_capabilities`, then apply workspace
  [routing policy](../worker-assembly.md#select-execution-under-workspace-policy). Set needed model/effort
  explicitly; catalog membership is not spare capacity. Approval modes may wait for humans, not enforce read-only isolation.
- Use `delegate_task` for T3-owned children, normally async, with a stable `clientRequestId` for retries of
  the same assignment. Retain `taskId`; `timeoutMs` in wait mode limits the parent's wait, not the child.
- `task_status.workState` distinguishes working, waiting_for_children and result_available. A returned turn
  or terminal parent status is not full descendant completion. Use status only when a decision needs it;
  normal completion notifications drive the owner's next-action decision, not polling.
- `childThreadId` is backing conversation storage, not task ownership. `t3_thread_send` after completion
  can create a fresh task: retain its new taskId; the original final stays final. Later child-thread runs
  do not reopen the original result; account for pending runs when determining safe replacement.
- Each independent review round uses a new `delegate_task`/clientRequestId with original brief, prior
  findings/responses and unresolved objections, not a send to the previous review's backing thread.

## Workspace, attention and transfer

- Separate/top-level conversations require explicit user intent; use `t3_thread_launch` with an explicit
  workspaceStrategy. Omission selects the project root, not necessarily the caller's worktree; shell cd
  cannot change the app binding. Child `isolation: worktree` starts at the local commit, without uncommitted edits.
- Handle `hasPendingQuestion` through supported pending-request tools or the user; do not confuse human
  approval waits with failed engineering. Use native attention/error facts for bounded diagnosis.
- `task_cancel` requests native stop, including later queued work/descendants under its documented scope.
  Confirm affected writers and mutating processes stopped before replacement; do not infer stop from a send,
  timeout or archived parent. A Supervisor handoff cannot reparent task IDs: old tasks retain their caller;
  retain domain owners through supported thread handoff or explicitly authorized replacement.
- Discover missing tools through supported discovery/transport. No Pi subagent plugin, subprocess pool,
  custom queue or watcher as a replacement. Authorized heartbeat/schedule bindings follow the active owner;
  changing cadence or source instructions does not revive paused jobs.

## Bounded Supervisor refill heartbeat binding

Under explicit rollout authority, inspect `list_scheduled_tasks` and update the exact existing active S job
with `update_scheduled_task`; retain its ID/binding, set structured interval 900000ms, report nextRunAt.
Do not create a duplicate timer or resume unrelated paused jobs. If no matching job exists, resolve the
binding under explicit authority before creation. Installation changes happen outside heartbeat ticks.
Use [refill](../refill.md) and the current supervisor prompt. Read existing local domain summaries plus
necessary native lifecycle/queue evidence; a volume-only capacity check is allowed. For a concrete gap,
`t3_thread_send` to the actual C with a stable clientRequestId for this correction, using queue mode;
first suppress equivalent queued/running work. Keep returned run/task IDs in native context, not a ledger.
Do not steer/restart an active owner merely to refill; do not call `delegate_task` from the heartbeat.
No direct engineering, file/state writes, forge refresh, tests, Git, cleanup, schedule change or self-queued
follow-up during ticks. A failed send is not delivery: report it without blind retry. A C reply/failure is
an ordinary execution event, not permission to bypass scope or quotas. Native Stop and ownership remain.

## When the provider is Pi

Pi's `agent_end` may precede retries, compaction or queued continuation; `agent_settled` is its final
notification, not proof that a T3-owned task's descendants are complete. Verify both lifecycle boundaries.
[Pi extras](pi-extras.md) provide opt-in same-task helpers only. Verify the actual runtime/API, exact extension
loading, command/tool exposure, RPC UI and final-settlement handling before enabling; local offline tests
are not live T3 acceptance. `/repostew-goal-stop` disarms a helper, not T3 task cancellation. Preserve host
Stop, permissions and original budgets; never hot-reload active C/W or treat structured reports as acceptance.
