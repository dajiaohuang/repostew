# Update role contracts without accumulating instructions

Use this procedure when an authorized policy editor changes a persistent role's methods or scope.
The selected host owns delivery and lifecycle; updating a contract does not grant new work or actions.

## 1. Find the authoritative source and its consumers

Identify the role's source modules, role-specific rules, generator, rendered file and deployment binding.
Check for saved inline startup instructions and compatibility entrypoints that can retain older text.
Keep current task facts and historical notifications separate from the fixed contract. An earlier
message remains historical evidence rather than another policy layer every successor must load.

Read affected current sections and reconcile unknown edits before changing shared sources. Record the
existing revision or a recoverable preimage using the project's normal mechanism. A snapshot preserves
bytes; it does not establish writer custody or authorize overwriting concurrent work.

## 2. Merge the meaning into the existing rule

For each new requirement, identify the existing rule it changes and choose its proper home:

- Shared methods belong in one reusable source; each affected role receives the applicable result.
- Role responsibilities and domain exceptions belong in that role's source.
- Identity, current owner, task progress, temporary holds and deployment revisions belong in facts.
- Superseded incidents and decisions remain in history, outside ordinary startup context.

Replace the affected rule instead of adding a dated override or repeating shared methods in a specialty.
Use a short operating sequence first and state the current rule directly. Preserve exact restrictions,
exceptions, privacy, original ownership, unknown operations and cumulative limits. A request that adds a
source does not silently replace another source or expand unrelated authority.

Review semantic coverage: where did each responsibility, permission, exception and stop condition go?
Shorter text is not necessarily better, and equal hashes or fewer bytes cannot prove preserved meaning.
Retire superseded generators so that a later rebuild cannot restore the old instruction stack.

## 3. Render and check the actual entrypoints

Generate from the revised source through the existing renderer, preserving concurrent edits and
unrelated runtime choices. Check the files and compatibility entrypoints that the role actually consumes.
Keep reusable rules free of deployment identities and local paths. Verify relevant links, role selection
and unchanged authority, rather than creating a new review or engineering-acceptance stage.

If an application instruction also exists as saved launch text, inspect the host's supported update
path. A file render alone does not update that separate input. Where no supported path exists, name
the remaining limitation; this guide is not permission to edit a private runtime database.

## 4. State which activation boundary was observed

Keep these claims separate in the existing deployment facts:

1. **Source/rendered:** the editor changed the intended source and generated files.
2. **Saved:** the host retained the intended inputs for a future start.
3. **Delivered:** the intended content reached the identified current occupant through an observed route.
4. **Adopted:** a relevant later action provides evidence that the occupant applied the changed rule.

Do not infer a later boundary from an earlier one. No later opportunity means adoption remains
unobserved. A read acknowledgement establishes only the read; it does not establish future compliance.
Use short change notifications that point to the current contract, rather than copying another full
contract into the task stream. Preserve existing tasks; a historical startup instruction is not new work.

Choose the next safe supported activation boundary for the actual host. Do not restart a healthy writer,
replay historical work or change sessions merely to make an update appear active.

## 5. Check one relevant later opportunity

At an existing natural work boundary, inspect the behavior the change was intended to affect. For
example, a priority update is exercised when the role selects its next eligible unit; a consolidation
rule is exercised when the next same-topic candidate is considered. A file check proves rendering,
not those decisions. An observed decision applies to that opportunity, not the role's whole future.

Investigate concrete contradictions through the original owner. Keep incomplete activation visible,
reuse valid evidence and continue independently authorized work. Do not add a watcher, repeated full
reads, per-tool approval or a universal receipt requirement.

See the [OpenRig field example](../../examples/openrig-context-updates/README.md) for a real source/render
correction and a separate saved-startup limitation. Native details remain in that example and the
[host adapters](harness.md); this procedure is portable application guidance.
