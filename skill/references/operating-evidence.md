# Evidence for sustained repository work

Use this method for an explicitly assigned operational audit or a concrete execution contradiction.
It does not add routine acceptance, polling, a second queue, or permission to restart or delete resources.
Ordinary contribution results keep their existing short return contract.

## Audit execution, then outcomes

1. Name the selected native task, current owner, source window and required outcome. Separate current
   occupants from migrated, stopped or historical records before interpreting a roster.
2. Bind available execution evidence to that occupant and task. Record the source, observation time and
   coverage gap. A stored conversation reference alone is not independent live-process identity proof;
   time proximity alone does not attribute a call to a task.
3. Distinguish a tool invocation, its returned result, an unfinished background operation, a model wait,
   a concrete external dependency and an ended unit. Silence alone proves none of them. Preserve handles
   and uncertain mutations; use the existing event/result route rather than starting another operation.
4. Inspect the promised effect only to the assigned audit's extent: a changed artifact, exact revision,
   submission, correction or disposition. Calls, claims and notes demonstrate activity, not delivery.
   An artifact's existence or hash establishes only the property actually checked.
5. Return actual effects, legal waits, contradictions and unknowns with their next owner. Keep source
   coverage, one engineering unit, the continuing mandate and resource disposition separate. Correct
   through the existing owner; an audit finding does not itself transfer custody.

Use a bounded report with fields already available from the host and project records:

| Claim | Minimum useful evidence | What it does not establish |
| --- | --- | --- |
| Current identity | Exact owner/binding and observation source | Historical records belong to today's occupant |
| Execution observed | Attributed invocation/result or live owned operation | Useful work or completion |
| Waiting | Named dependency, responsible owner and release condition | Every other unit must stop |
| Delivery | Actual object/revision and the checked effect | Review, merge or deployment |
| Coverage | Selected input and processed/retained remainder | A local partial is whole-scope completion |

Keep raw prompts, credentials, private findings and unrelated output out of summaries and public examples.
Unavailable evidence remains unknown. Counts and elapsed times are observations, not performance or
causal improvement claims without a suitable comparison.

## Maintain context at its source

Use the [contract-update procedure](context-updates.md) to merge new requirements into current rules,
render from authoritative sources and reconcile saved startup inputs. Source/rendered, saved, delivered
and adopted remain separate observations. The procedure owns this method; this page does not add a
second contract-maintenance policy. Native mechanics stay in the selected host adapter.

## Resource use and cleanup results

At resource creation and natural phase boundaries, retain the producer, engineering owner, consumers,
disposition owner, exact resource and purpose/release condition in existing task or project facts.
Explicit declarations aid investigation; a missing record, expired lease or empty process scan does not
authorize disposal. Reuse valid facts and investigate changed inputs instead of rescanning unchanged
history. Use [storage's existing release authority and paths](storage.md).

Report separately: newly released resources; retained resources and their current purpose; exact owner
or use unknowns; and rechecks of historical receipts. Rechecking an old deletion is not a new deletion.
Logical path bytes, link removals and volume-free observations are different facts, with no automatic
physical-reclamation attribution. An authorized cleanup audit may inspect exact receipts and current
state; it does not add per-file audit gates to ordinary task cleanup or override scoped minimal retention.

## Publication and continuous responsibility

Before a new public object, inspect the applicable existing contribution and choose extension of the
same object, consolidation, an independent contribution, or local retention. Reuse current checks and
record the reason only where a decision is material; this is not Coordinator approval or a numerical
posting quota. Common-root fixes and a shared document topic normally extend one reviewable object;
independent concerns or a maintainer's scope request can require separation.

Give unsatisfied human maintainer requirements first priority within the authorized scope. Preserve the
original writer and update the same branch/object. A reviewable Draft can precede remaining validation
where target and assignment allow it; target-specific rules and meaningful necessary checks still apply.
Draft, ready, review, merge and deployment are distinct outcomes with their assigned owners. Later
feedback returns through the existing route, without making one PR's wait block independent engineering.

A persistent repository custodian and a bounded executor are optional responsibility arrangements, not
mandatory new roles. Reuse the existing Coordinator/Worker contract and native work lifecycle. An intake
or migration unit finishing does not finish a standing repository mandate; an idle worker with no legal
unit need not manufacture work. Source discovery and recurrence remain separately authorized.
